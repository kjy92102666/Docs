### 2. Provider 인터페이스

**명시적 공통 인터페이스**  
`pcb-defects-mes/backend/app/features/chatbot/providers/base.py:5`:

```python
@dataclass(frozen=True)
class ProviderMessage:
    role: str
    content: str

class ChatProvider(Protocol):
    async def generate(
        self,
        messages: Sequence[ProviderMessage],
    ) -> str:
        ...


따라서 `ollama_provider.py`가 사실상의 유일한 인터페이스인 것은 아닙니다. `typing.Protocol` 기반의 구조적 인터페이스가 명시되어 있습니다.

**추상 클래스(ABC)는 아님**

- 상속할 필요 없이 `async generate(messages) -> str`만 만족하면 됨
    
- `@runtime_checkable`은 없으므로 런타임 `isinstance()` 검사용 인터페이스는 아님
    
- `chat`, `stream` 메서드는 없음
    
- Provider 이름, 모델명, 사용량 같은 메타데이터도 인터페이스에 없음
    

**ollama_provider.py 전체 클래스/메서드 시그니처**

### 5. 에러 처리 패턴

#### 설정 검증

`OllamaSettings`는 다음을 검사합니다:

- 빈 `OLLAMA_BASE_URL` → `OllamaConfigurationError`
    
- 빈 `OLLAMA_MODEL` → `OllamaConfigurationError`
    
- 숫자가 아닌 timeout → `OllamaConfigurationError`
    
- 0 이하 timeout → `OllamaConfigurationError`
    
- URL 형식 자체는 검증하지 않음

```
#### 호출 오류 매핑 표

| **발생 조건**                    | **Provider 예외**              | **HTTP 변환**                   |
| ---------------------------- | ---------------------------- | ----------------------------- |
| `httpx.ConnectError`         | `OllamaUnavailableError`     | `503 OLLAMA_UNAVAILABLE`      |
| `httpx.TimeoutException`     | `OllamaTimeoutError`         | `504 OLLAMA_TIMEOUT`          |
| `HTTP 404`                   | `OllamaModelError`           | `502 OLLAMA_MODEL_ERROR`      |
| 기타 HTTP 오류                   | `OllamaUnavailableError`     | `503 OLLAMA_UNAVAILABLE`      |
| 잘못된 JSON                     | `OllamaInvalidResponseError` | `502 OLLAMA_RESPONSE_INVALID` |
| `message` 객체 누락              | `OllamaInvalidResponseError` | `502 OLLAMA_RESPONSE_INVALID` |
| `message.content` 누락/비문자열/공백 | `OllamaInvalidResponseError` | `502 OLLAMA_RESPONSE_INVALID` |
내부 예외 메시지는 HTTP 응답으로 그대로 노출하지 않고 사용자용 `code/message/guidance`로 교체합니다.

확인된 예외 처리 공백도 있습니다:

- 빈 `messages`는 `ValueError`이며 Provider 전용 HTTP 오류로 매핑되지 않음
    
- JSON 최상위 값이 객체가 아니라 배열이나 null이면 `data.get()`에서 일반 예외가 날 수 있음
    
- 모든 404를 “모델 없음”으로 간주함
    
- 401/403/429처럼 클라우드 Provider에서 중요한 인증·권한·rate-limit 분류는 없음
    
- DNS·TLS 등 `ConnectError`/timeout/HTTP status 외 httpx 오류 전체를 포괄하지 않음
    

### 6. OpenAI Provider 재사용 가능성

#### 그대로 재사용 가능한 부분

- `ProviderMessage`
    
- 비스트리밍 `ChatProvider.generate(messages) -> str` 계약
    
- 요청의 `message`, `context_hints`
    
- `reply`, `contexts_used` 중심 응답 구조
    
- capability 선택 로직
    
- Dashboard/Inspection 데이터 컨텍스트 생성
    
- 정적 지식
    
- 시스템 프롬프트
    
- 서비스의 system/user 메시지 구성
    
- `/api/chatbot/messages` 라우트 경로
    
- FastAPI `Depends()` 기반 Provider 주입
    
- `detail.code/message/guidance` 형태의 사용자 안전 오류 응답
    
- 테스트용 가짜 Provider/의존성 override 방식
    

OpenAI도 완성된 답변을 한 번에 반환하는 방식으로 구현한다면 현재 Protocol과 서비스 흐름을 거의 그대로 유지할 수 있습니다.

#### OpenAI용으로 새로 필요한 부분

- OpenAI 설정 클래스: API key, 모델, base URL 사용 여부, timeout
    
- 인증 헤더 또는 SDK client 초기화
    
- OpenAI 요청 payload 작성
    
- OpenAI 응답에서 텍스트 추출
    
- 인증 실패, 권한 오류, rate limit, 모델 오류, timeout, 서버 오류 매핑
    
- `CHATBOT_PROVIDER` 기반 분기나 Provider factory
    
- OpenAI 설정 오류의 HTTP 변환
    
- `ChatResponse.provider`를 실제 Provider에 맞게 설정하는 방법
    

특히 현재 `pcb-defects-mes/backend/app/features/chatbot/service.py:133`는 모든 반환 경로에서 `provider="ollama"`를 하드코딩합니다. 직접 LLM을 호출하지 않는 운영 데이터 단축 응답도 Ollama로 표시됩니다.

`pcb-defects-mes/backend/app/features/chatbot/router.py:19` 역시 Ollama 예외 클래스를 직접 import해서 분기합니다. 따라서 OpenAI Provider 클래스만 추가하면 전환되는 구조는 아닙니다.

OpenAI 호출 구현을 기존 httpx로 할지 공식 SDK를 추가할지는 확인 필요입니다. 현재 공식 OpenAI SDK와 LangChain은 의존성에 없습니다. 새 라이브러리를 추가하면 저장소 규칙상 사유를 명시하고 리뷰가 필요합니다.

#### 스트리밍 차이

현재 Ollama도 스트리밍 기능을 사용하지 않으므로, OpenAI를 비스트리밍으로 구현한다면 근본적인 인터페이스 차이는 없습니다.

OpenAI 스트리밍을 도입하려면 다음까지 변경해야 합니다:

- `generate() -> str` 계약을 `async iterator` 형태로 확장
    
- 라우터를 SSE 또는 chunked streaming으로 변경
    
- 프론트의 일반 JSON 요청을 스트림 소비 방식으로 변경
    
- 부분 응답·중단·오류 처리 추가
    

어떤 OpenAI API 방식과 스트리밍 이벤트 형식을 사용할지는 현재 코드에 결정된 내용이 없으므로 확인 필요입니다.
