## 2. 순차 부하 테스트 (배치 크기 확장)

기존 시딩된 `production_plan`(1~4)이 전부 소진된 상태라, 신규 계획을 등록해 순차적으로 배치 크기를 늘려가며 테스트.

**절차**: `POST /api/plans/{id}/batch` → `POST /api/batches/{id}/line-transfer/complete` → `POST /api/inspection/batches/{id}/start`(실제 YOLO, 시뮬레이션 API 아님)

| 배치           | 개수      | 소요시간     | 개당 시간      | 메모리           | CPU                      |
| ------------ | ------- | -------- | ---------- | ------------- | ------------------------ |
| 배치           | 개수      | 소요시간     | 개당 시간      | 메모리           | CPU                      |
| batch 5      | 20      | 18초      | 0.9초*      | (미관찰)         | (미관찰)                    |
| batch 6      | 50      | 14초      | 0.28초      | 450MiB        | 0.13~0.15%(관찰 타이밍 놓침 추정) |
| batch 7      | 100     | 26초      | 0.26초      | 483MiB        | 98~99%                   |
| batch 8      | 200     | 53초      | 0.265초     | 450~514MiB    | 97~99%                   |
| batch 9      | 360     | 79초      | 0.219초     | 476MiB(거의 고정) | 98~99%, 순간 108%          |
| **batch 10** | **500** | **123초** | **0.246초** | **511MiB**    | **97~108%**              |

*최초 실행은 모델 lazy loading 오버헤드 포함

**관찰 결과**:
- 메모리는 전 구간 450~514MiB, 전체 한도(3.744GiB) 대비 **13% 내외**로 안정적. 배치 크기가 커져도 누적되지 않음(메모리 누수 없음 확인)
- 개당 처리 속도 0.22~0.28초로 일정, 배치 크기와 무관하게 선형적으로 확장됨
- CPU는 검사 중 97~108%(2 vCPU 중 1개 소진 수준), 완료 즉시 1% 이하로 복귀
- `YOLO_MAX_CONCURRENCY=1`이 프로세스 전역 세마포어(`asyncio.Semaphore`)로 확인됨 — 배치별이 아니라 시스템 전체에서 YOLO 추론을 1개씩만 순차 실행하도록 강제. 이게 CPU 폭주를 막는 핵심 장치임을 코드로 확인
- 서버는 `nproc` 확인 결과 **2 vCPU**

## 3. 동시성 부하 테스트 (여러 라인 동시 검사)

**계기**: 순차 테스트는 "배치 1개씩"만 검증했을 뿐, 발표 시연 중 실제로 벌어질 수 있는 "여러 라인이 동시에 검사되는 상황"은 검증되지 않았다는 지적에 따라 추가 진행. 라인이 8개이므로, 동시 검사 가능한 배치의 실질적 상한도 8개(라인 점유 제약상 배치당 1개 라인 필요, 대기 슬롯은 검사 중이 아니므로 부하 없음).

**방법**: `Start-Job`으로 여러 배치의 `/start` 요청을 병렬 발사, 각 배치는 20개로 통일(동시성 자체 검증이 목적이라 개수는 작게 유지)

| 동시 배치 수 | 총 이미지 | 소요시간 | 개당 시간 | CPU 최고치 | 메모리 범위 |
|---|---|---|---|---|---|
| 2개 (batch 11,12) | 40 | 10초 | 0.25초 | 98~99% | 465~508MiB |
| 4개 (batch 13~16) | 80 | 19~20초 | 0.24초 | 100.3% | 499~519MiB |
| 6개 (batch 17~22) | 120 | 29~30초 | 0.25초 | 100.35% | 498~522MiB |
| **8개** (batch 23~30, 전체 라인) | **160** | **40~41초** | **0.25초** | **167.94%** | **501~510MiB** |

**관찰 결과**:
- 동시 배치 개수와 무관하게 **개당 처리 속도가 0.24~0.25초로 완전히 일정** — 순차 테스트 때(0.22~0.28초)와도 정확히 같은 범위
- 메모리는 465~522MiB 사이, 순차 테스트 때(450~514MiB)와 사실상 동일한 범위 — 동시 실행이 메모리 부담을 늘리지 않음
- CPU는 1~6개 동시 실행까지 100% 근처(2코어 중 1코어 수준)로 유지되다가, **8개 전체 동시 실행에서 처음으로 167.94%(2코어 대부분 사용) 관측** — 다만 순간 피크 이후 즉시 99%대로 안정, 완료 후 정상 복귀. 위험 신호가 아니라 "2코어를 최대로 활용" 수준으로 판단
- 모든 동시성 구간에서 에러·실패·중복 처리 없이 전 배치 정상 완료(`job_status: COMPLETED`, `completed_count == total_count`)

## 4. 종합 결론

**➡️ 4GB 서버로 충분함. 8GB 증설 불필요.**

- 단일 배치 500개, 8개 라인 동시 검사(총 160개) 양쪽 모두 메모리 13% 내외, CPU는 세마포어로 예측 가능하게 관리됨
- `YOLO_MAX_CONCURRENCY=1` 설계가 "동시에 여러 배치가 몰려도 CPU 폭주 없이 순차 처리"라는 안전장치로 정확히 작동함을 실측 확인
- 처리 속도는 배치 크기·동시 실행 개수와 무관하게 PCB 1개당 약 0.22~0.28초로 일정 → **8개 라인이 각 500개씩 동시에 돈다고 가정해도(4,000장), 대략 4,000 × 0.25초 ≈ 1,000초(약 17분) 안에 전량 처리 가능**하다는 예측 근거 확보(단, 이 최대 규모 조합은 아직 실측 안 됨, 아래 참고)

**어제 작업일지의 Go/No-Go 기준(8/17: 서버 YOLO 추론 실패 시 8GB 증설) → 통과로 최종 확정.**

## 5. 아직 실측하지 않은 것 (참고, 필요시 8/18~19 여유 시간에 추가 검증)

- **"8개 라인 각각 대용량(500개)으로 동시 실행"은 검증하지 않음** — 오늘은 순차(단일 배치 대용량)와 동시성(다수 배치 소량)을 각각 따로 확인했을 뿐, 두 축을 합친 최악의 조합(8×500=4,000장 동시)은 시도하지 않았음. 다만 각 축의 특성(속도 일정, 메모리 비례하지 않음)을 볼 때 문제없을 것으로 예측되나, 완전한 실증은 아님
- 위 결론에 따라 **8GB 증설 시 Ollama 병행 가능성 측정**(어제 남겨둔 To-Do)은 증설 자체가 불필요해졌으므로 **더 이상 검토하지 않음**
- **"당일 계획 배치만 검사 화면에 노출"**은 팀의 의도된 UI 설계로 확인됨(버그 아님) — 발표 종료 후 고도화 항목으로 이월(계획/배치 등록은 미래 날짜도 가능하나 검사 담당자 화면에는 당일만 노출)
- `INSPECTION_MODE` 환경변수가 죽은 설정이라는 점 — `.env.example`에서 정리하거나, 반대로 실제로 두 엔드포인트를 전환하는 용도로 리팩터링할지 결정 필요(발표 후)
