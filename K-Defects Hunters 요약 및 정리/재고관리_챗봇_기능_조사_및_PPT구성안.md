# 재고관리·챗봇 기능 조사 및 PPT 구성안

> 현재 소스 기준 조사 결과. 재고 관리는 실제 DB 재고를 조회·판정·차감하는 업무 기능까지 구현되어 있고, 챗봇은 MES 설명과 Dashboard·검사 배치 데이터를 AI 모델에 연결하는 구조로 확인됨.

---

## 1. 발표 핵심 요약

> "검사가 끝난 PCB 배치가 SMD 공정으로 넘어가기 전에 BOM과 현재 부품 재고를 비교하여 생산 가능 여부를 자동 판정하고, 인계 시 재고를 안전하게 차감합니다. 챗봇은 사용자의 질문을 분석하여 문서 지식이나 실시간 Dashboard·검사 데이터를 선택하고, Ollama 또는 OpenAI 모델을 통해 답변합니다."

# PPT 구성안

## 슬라이드 1. 기능 도입 배경

### 화면에 넣을 내용
- PCB 검사 완료 후 SMD 공정으로 넘어가기 전 자재 확인 필요
- 작업자가 BOM과 재고를 수작업으로 비교하면 누락·계산 오류 발생 가능
- MES 화면에서 생산 가능 여부를 자동 판정
- 사용자가 복잡한 MES 데이터를 자연어로 질문할 수 있도록 AI 챗봇 제공

### 발표 멘트
> "본 시스템에서는 PCB 비전 검사에서 끝나는 것이 아니라, 검사 결과를 실제 다음 생산 공정과 연결합니다. 검사 결과 양품으로 판정된 PCB 수량을 기준으로 필요한 SMD 부품을 계산하고, 현재 재고로 생산 가능한지를 판단합니다. 또한 사용자가 Dashboard와 검사 데이터를 직접 찾아보지 않고 자연어로 질문할 수 있도록 챗봇을 구성했습니다."

## 슬라이드 2. 전체 시스템 구조

```
[React Frontend]
  ├─ 재고 관리 화면
  └─ MES 챗봇
          │ REST API
          ▼
[FastAPI Backend]
  ├─ Inventory API
  │    ├─ BOM 소요량 계산
  │    ├─ 재고 상태 판정
  │    └─ SMD 인계 트랜잭션
  │
  └─ Chatbot API
       ├─ 질문 유형 분석
       ├─ Dashboard/Batch 데이터 조회
       ├─ 시스템 설명 Context 구성
       └─ Ollama 또는 OpenAI 호출
          │
          ▼
[MySQL/MariaDB]
  ├─ production_batch
  ├─ production_plan
  ├─ product_model
  ├─ bom_item
  ├─ part
  └─ batch_material_consumption
```

### 발표 멘트
> "프론트엔드는 React, 백엔드는 FastAPI, 데이터베이스는 MySQL 계열 구조입니다. 재고 관리는 생산 배치, 제품 모델, BOM, 부품 재고를 조합합니다. 챗봇은 DB에 직접 임의 SQL을 생성하는 방식이 아니라, 백엔드에서 허용한 Dashboard와 Batch 서비스만 호출한 뒤 그 결과를 AI 모델의 Context로 전달합니다."

## 슬라이드 4. 배치별 자재 소요량 계산

### 계산 기준

```
배치별 부품 소요량 = 검사 결과 정상 PCB 수 × PCB 1개당 BOM 소요량
```

**예시**
- 정상 PCB 수: 100개
- 저항 R-101 BOM 수량: PCB당 4개
- 필요 수량: 100 × 4 = 400개
- 현재 재고: 350개
- 추가 필요 수량: 400 - 350 = 50개

### 배치가 재고 큐에 들어오는 조건
- 배치 상태가 `INSPECTED`
- `normal_PCB_count`가 존재
- 정상 PCB 수가 0보다 큼
- 아직 `smd_handoff_at`이 기록되지 않음

> 즉, 검사하지 않은 배치나 이미 SMD로 인계된 배치는 재고 대기 목록에 나타나지 않습니다.

### 재고 판정 기준

| 판정               | 기준            | 의미                |
| ---------------- | ------------- | ----------------- |
| 충분 ENOUGH        | 재고/소요량 ≥ 1.5  | 여유 재고 확보          |
| 발주 필요 ORDER_NEED | 1.0 이상 1.5 미만 | 생산 가능하지만 재고 여유 부족 |
| 대기 PENDING       | 1.0 미만        | 현재 재고로 생산 불가능     |

추가 필요 수량 계산식:

```
max(소요량 - 현재 재고, 0)
```

> 판정 로직: `backend/app/features/inventory/calc.py:9`

### 발표 멘트
> "재고 판정은 단순히 재고가 0인지 확인하는 방식이 아닙니다. 검사에서 정상으로 확인된 PCB 수와 제품 BOM을 곱해 실제 필요한 수량을 계산합니다. 필요 수량보다 재고가 적으면 대기 상태가 되고, 생산은 가능하지만 여유가 적으면 발주 필요 상태로 구분합니다."

## 슬라이드 5. SMD 인계와 데이터 정합성

### 인계 처리 과정
1. 사용자가 배치 상세에서 SMD로 인계 선택
2. 프론트엔드가 진행 가능 여부 확인
3. 백엔드가 배치 상태를 다시 검증
4. DB 트랜잭션 시작
5. 대상 배치와 부품 재고 행에 `FOR UPDATE` 잠금
6. 잠긴 최신 재고로 생산 가능 여부 재계산
7. 부품별 재고 차감
8. 자재 소비 이력 저장
9. `smd_handoff_at` 기록
10. 트랜잭션 커밋
11. WebSocket으로 다른 화면에 인계 이벤트 전달

> 핵심 로직: `backend/app/features/inventory/service.py:92`

### 동시성 제어가 필요한 이유

작업자 A와 B가 같은 부품을 사용하는 서로 다른 배치를 동시에 인계할 수 있습니다.

**잠금이 없다면:**
```
현재 재고 100개
A 필요량 70개 → 가능 판정
B 필요량 60개 → 가능 판정
최종 재고 -30개
```

현재 구현은 `SELECT ... FOR UPDATE`로 부품 재고를 잠그기 때문에 먼저 처리된 인계 이후의 최신 재고를 두 번째 요청이 확인합니다. 부족하면 `409 INSUFFICIENT_STOCK`으로 거부됩니다.

### 원자성

다음 작업은 하나의 트랜잭션으로 처리됩니다.
- `part.stock_qty` 차감
- `batch_material_consumption` 소비 이력 저장
- `production_batch.smd_handoff_at` 기록

중간에 하나라도 실패하면 전체가 롤백되므로 "재고만 줄고 인계 기록은 없는 상태"를 방지합니다.

### 발표 강조점
> "프론트 버튼 비활성화만 믿지 않고 서버가 최신 재고를 다시 검증한다."

이 부분이 시스템 안정성을 설명할 때 가장 중요한 포인트입니다.

## 슬라이드 6. 재고 API와 실시간 갱신

### API 구성

| 메서드 | API | 역할 |
|---|---|---|
| GET | `/api/inventory/parts` | 전체 부품 재고 및 안전재고 조회 |
| GET | `/api/inventory/queue` | 인계 대기 배치와 요약 지표 조회 |
| GET | `/api/inventory/batches/{id}/requirements` | 배치별 필요 자재 조회 |

### 갱신 방식
- 기본적으로 30초 간격 폴링

- 네트워크 오류 발생 시 재시도 UI 제공

### 시스템적 의미

## 슬라이드 8. 챗봇 질문 처리 구조

### 처리 순서

```
사용자 질문
   ↓
질문 키워드 및 context_hints 분석
   ↓
필요한 Capability 선택
   ├─ docs       : 시스템·기능 설명
   ├─ dashboard  : 오늘 검사 수량, 불량률, KPI
   └─ inspection : Batch 상태, 라인, NG 수
   ↓
백엔드 서비스에서 실제 데이터 조회
   ↓
시스템 프롬프트 + 선택된 Context + 질문 구성
   ↓
Ollama 또는 OpenAI 호출
   ↓
답변 반환
```

> 질문 분류와 Context 구성: `backend/app/features/chatbot/service.py:125`, `backend/app/features/chatbot/capabilities.py:190`

### 질문 분류 예시

| 질문 | 사용 데이터 |
|---|---|
| "MES 시스템 기능 설명해줘" | 정적 프로젝트 지식 |
| "오늘 검사 현황 알려줘" | Dashboard 데이터 |
| "현재 배치 상태 알려줘" | Batch/검사 데이터 |
| "오늘 불량 PCB 몇 개야?" | Dashboard 데이터로 직접 계산 |
| "현재 AGV 위치 알려줘" | 지원하지 않는 실시간 데이터로 명시적 거부 |
| "현재 재고 몇 개야?" | 현재 챗봇 미연결 영역으로 명시적 거부 |

### 환각 방지 정책

시스템 프롬프트에는 다음 원칙이 포함됩니다.
- 제공된 프로젝트 설명과 현재 데이터만 사용
- Context에 없는 수치·위치·이력을 추측하지 않음
- 데이터 0건과 데이터 미제공을 구분
- 존재하지 않는 기능을 만들어내지 않음
- 현재 상태를 일반 지식으로 추정하지 않음
챗봇은 별도 메뉴가 아니라 모든 MES 화면에서 사용할 수 있는 공통 도우미입니다. 사용자가 메시지를 보내면 전송 중에는 입력을 차단하여 중복 요청을 방지하고, 서버 오류가 발생하면 단순 실패 문구가 아니라 원인과 조치 안내를 함께 표시합니다.
### 발표 포인트
> "챗봇은 별도 메뉴가 아니라 모든 MES 화면에서 사용할 수 있는 공통 도우미입니다. 사용자가 메시지를 보내면 전송 중에는 입력을 차단하여 중복 요청을 방지하고, 서버 오류가 발생하면 단순 실패 문구가 아니라 원인과 조치 안내를 함께 표시합니다.LLM이 DB를 자유롭게 탐색하는 구조가 아니라, 백엔드가 허용한 데이터를 선택하여 전달하는 제한된 Context 방식입니다."

## 슬라이드 9. Ollama와 OpenAI Provider 구조

### 기본 설정
- 기본 Provider: Ollama
- 기본 모델: `qwen3:0.6b`
- 기본 주소: `http://127.0.0.1:11434`
- 기본 제한 시간: 60초
- `CHATBOT_PROVIDER=openai` 설정 시 OpenAI 사용 가능
- OpenAI 기본 모델: `gpt-4o-mini`
- 두 Provider 모두 현재 비스트리밍 방식

### Provider 추상화

```
Chatbot Service
      │
      ▼
ChatProvider Protocol
  ├─ OllamaProvider
  └─ OpenAIProvider
```

서비스 계층은 어떤 AI가 사용되는지 알 필요가 없고, 공통 `generate(messages)` 계약만 사용합니다. 따라서 로컬 AI와 외부 API를 환경변수로 교체할 수 있습니다.

### Ollama 장점
- 외부 API 키 불필요
- 로컬 실행으로 데이터 외부 전송 최소화
- 비용 부담 감소
- 인터넷 연결 없이 사용 가능

### OpenAI 장점
- 상대적으로 높은 자연어 이해·생성 품질
- 복잡한 질문 처리에 유리
- 로컬 PC 성능에 덜 의존

### 오류 처리

Ollama는 다음 오류를 구조화하여 반환합니다.

| 상황 | 상태 코드 |
|---|---|
| 서비스 연결 불가 | 503 |
| 응답 시간 초과 | 504 |
| 모델 없음 | 502 |
| 잘못된 응답 형식 | 502 |
| 환경설정 오류 | 500 |

사용자에게 내부 예외를 그대로 노출하지 않고 `{code, message, guidance}` 형식으로 전달합니다.

- 부족 자재 조기 발견

- 배치별 자재 소비 이력 확보
- 다중 작업자 환경에서 상태 동기화

### 챗봇이 제공하는 가치
- MES 기능 설명 지원
- Dashboard·Batch 데이터의 자연어 조회
- 사용자의 화면 탐색 시간 단축
- 지원하지 않는 데이터는 추측하지 않고 거부
- 로컬/클라우드 AI 교체가 가능한 구조

### 최종 발표 문장
> "이 프로젝트는 AI 비전 검사 결과를 보여주는 데서 끝나지 않고, 검사 결과를 자재 재고와 SMD 인계까지 연결합니다. 챗봇은 이 운영 데이터를 사용자가 자연어로 접근할 수 있도록 돕는 인터페이스 역할을 합니다."

# 현재 구현의 한계

발표에서 구현 완료 범위와 향후 개선 범위를 정확히 구분해야 합니다.

### 재고 관리
- 발주서 자동 생성 기능은 없음
- SMD 인계 취소·복구 기능 없음
- 자재 입고·재고 조정 화면 없음
- 소비 이력 조회 화면은 아직 없음
- 기간별 재고 분석 기능 없음
- BOM이 없는 배치는 현재 로직상 진행 가능으로 판정될 수 있어 데이터 무결성 보완 필요
- 실제 MySQL을 연결한 동시 요청 통합 테스트보다 repository mock 기반 테스트 비중이 큼

### 챗봇
- 현재 대화 이력을 다음 요청에 전달하지 않음 (화면에는 메시지가 남지만 서버에는 매번 현재 질문 하나만 전송)
- 스트리밍 응답이 아니라 답변 완성 후 한 번에 표시
- LangChain, 벡터 DB, 임베딩 기반 RAG는 구현되지 않음
- 실시간 조회 범위는 Dashboard와 Batch/검사 데이터로 제한
- 재고 관리 기능은 실제 구현되어 있지만 챗봇의 정적 지식에는 아직 "재고 화면은 UI 자리만 있음"이라는 오래된 설명이 남아 있음 → `backend/app/features/chatbot/knowledge.py:29` 갱신 필요
- 챗봇에서 현재 재고 수량을 묻는 질문은 의도적으로 거부됨
- OpenAI Provider 코드는 존재하지만 README와 환경변수 예시는 아직 Ollama 중심
- OpenAI 실행 중 예외는 Ollama만큼 세분화된 HTTP 오류 매핑이 되어 있지 않음
- 사용자 인증, 질문별 권한 제어, 요청 속도 제한은 챗봇 코드에서 확인되지 않음
- 직접 계산하는 "불량 PCB 수"는 검사 수 × 불량률을 반올림하므로 정확한 원본 NG 개수와 차이가 날 가능성이 있음

발표에서는 따라서 "전체 MES 데이터를 조회하는 챗봇"이 아니라 다음과 같이 표현하는 것이 정확합니다.

> "현재는 시스템 설명, Dashboard, PCB 검사·Batch 현황을 지원하는 제한형 MES 챗봇이며, 재고·AGV 등 다른 운영 데이터 연동은 확장 단계입니다."

# 예상 질문과 답변

### Q. 재고가 동시에 차감되면 음수가 될 수 있지 않나요?
"백엔드가 트랜잭션 안에서 배치와 부품 재고를 `FOR UPDATE`로 잠근 뒤 최신 재고를 다시 확인합니다. 따라서 두 작업자가 동시에 요청해도 먼저 처리된 요청 이후의 재고를 기준으로 두 번째 요청이 재검증됩니다."

### Q. 왜 생산계획 생성 시점이 아니라 SMD 인계 시점에 재고를 차감하나요?
"계획만 생성된 상태에서는 실제 생산 수량이 확정되지 않았기 때문입니다. 비전 검사 결과 정상 PCB 수가 확정된 뒤, 실제 다음 공정으로 넘어가는 시점에 차감하여 계획 수량과 실제 양품 수량의 차이를 반영했습니다."

### Q. 챗봇이 잘못된 수치를 말할 가능성은 없나요?
"LLM에 전체 시스템을 자유롭게 추측하도록 하지 않고, 백엔드가 선택한 Dashboard와 Batch 데이터를 Context로 제공합니다. 지원하지 않는 재고·AGV 실시간 질문은 답을 생성하지 않고 조회할 수 없다고 반환합니다."

### Q. Ollama와 OpenAI를 모두 쓰는 이유는 무엇인가요?
"Ollama는 데이터 외부 전송과 비용을 줄이는 로컬 운영에 적합하고, OpenAI는 복잡한 자연어 처리 품질에 장점이 있습니다. Provider 인터페이스를 공통화하여 환경에 따라 선택할 수 있도록 구성했습니다."

### Q. 챗봇이 DB에 직접 SQL을 실행하나요?
"아닙니다. 챗봇은 기존 Dashboard와 Batch 서비스에서 정해진 데이터를 조회하고 이를 Context로 사용합니다. LLM이 임의 SQL을 생성하거나 데이터베이스를 직접 수정하지 않습니다."
