

제시해주신 설계안은 **단일 프론트엔드/클라이언트 환경에서 다수의 실시간 화면(Dashboard, ProcessStatus, PcbInspection)을 동기화하고, 생산-검사 공정 간 상태 충돌을 방지하는 매우 표준적이고 견고한 구조**입니다.

제안하신 방향을 바탕으로 실무 구현 시 시스템의 완성도와 안정성을 극대화할 수 있는 **핵심 설계 보완점 및 구체적 가이드**를 정리해 드립니다.

## 1. WebSocket 통합 및 이벤트 버스(Event Bus) 패턴

단일 `/ws` 연결 구조를 도입할 때 가장 중요한 것은 **App 최상단에서 단일 연결을 유지**하면서, 하위 컴포넌트들이 필요하지 않은 이벤트로 인해 **불필요한 리렌더링(Re-render)을 겪지 않도록 분리**하는 것입니다.

### 추천 클라이언트 Architecture

- **Global Provider / Custom Hook**: `/ws` 연결 및 자동 재연결(Exponential Backoff), Heartbeat(Ping/Pong) 관리를 담당합니다.
    
- **이벤트 구독(Publish-Subscribe) 분리**: React 기준, `events` 배열 전체를 Props로 넘기면 모든 컴포넌트가 매 이벤트 발생 시 리렌더링됩니다. `useSubscription('inspection.pcb.completed', handler)` 형태의 **이벤트 버스/구독 패턴**을 적용하는 것이 좋습니다.
    

TypeScript

```
// 백엔드 이벤트 계약 구조화 예시
interface SystemEvent<T = any> {
  type: string;          // 예: 'inspection.pcb.completed'
  domain: 'production' | 'inspection' | 'agv';
  event_version: number;
  event_id: string;      // UUID 또는 멱등성 키
  event_seq: number;     // Batch 내 순서 (이전 seq보다 작거나 같으면 무시)
  occurred_at: string;
  line_id: number;
  batch_id: number;
  payload: T;
}
```

### 재연결 시 상태 복구 (State Reconciliation) Strategy

Network Flapping 등으로 WebSocket 연결이 끊겼다 재연결될 때, 메시지 유실(Loss)이 발생할 수 있습니다.

1. 재연결 성공 시 (`onOpen`) 백엔드에 **`GET /api/v1/lines/{line_id}/current-state`** 요청을 보냅니다.
    
2. 백엔드는 현재 Line의 `phase`, `productionProgress`, `inspectionProgress`, 마지막 처리된 `event_seq`를 응답합니다.
    
3. 클라이언트는 REST API로 받아온 최신 스냅샷으로 Local Reducer State를 **덮어쓰기(Reconcile)** 합니다.
    

## 2. 생산 vs 검사 진행률 상태 분리 및 UI 표현

생산(Production)과 검사(Inspection)는 수율(Yield)과 속도(Tact Time)가 다르기 때문에 데이터 모델의 완벽한 분리가 필수적입니다.

### Data Model 구조화

JSON

```
{
  "line_id": 2,
  "batch_id": 101,
  "batch_size": 200,
  "phase": "INSPECTING", 
  "production": {
    "completed_qty": 200,
    "progress_percent": 100.0,
    "status": "COMPLETED"
  },
  "inspection": {
    "total_target": 200,
    "inspected_qty": 80,
    "ok_qty": 76,
    "ng_qty": 4,
    "progress_percent": 40.0,
    "current_pcb_id": "PCB-00180",
    "status": "IN_PROGRESS"
  }
}
```

### 공정 단계별 UI display 규칙

제시해주신 규칙에 **생산과 검사가 병행(Pipeline)되는 상황**까지 고려해 명확히 정리할 수 있습니다.

|**공정 단계 (phase)**|**생산 진행률 Bar**|**검사 진행률 Bar**|**대표 메인 Indicator**|
|---|---|---|---|
|**`PRODUCING`** (생산 중)|`production.progress` (0~99%)|0% (대기)|**생산 진행률** 표시|
|**`INSPECTING`** (검사 중)|100% (완료)|`inspection.progress` (0~99%)|**검사 진행률** 표시|
|**`INSPECTED`** (검사 완료)|100%|100%|**100% (적재 대기)**|
|**`TRANSFERRING`** (AGV 이송)|100%|100%|**이송 중 (AGV 태그)**|
|**`IDLE` / `WAITING`**|0%|0%|**대기 중**|

## 3. 타이머(Local Simulation) vs 실시간 이벤트 간의 충돌 방지

제시해주신 내용 중 "검사 이벤트가 기존 updateProduction()의 로컬 타이머와 경쟁하지 않도록 함"이 가장 뛰어난 통찰입니다. 프론트엔드 시뮬레이션 타이머와 실제 백엔드 이벤트가 섞이면 Progress Bar가 진동(Jittering)하거나 뒤로 밀리는 현상이 발생합니다.

### 해결 가이드

1. **역할 분담 원칙**:
    
    - **생산 공정**: 백엔드 이벤트가 뜸하다면 local timer 기반으로 Smooth animation/progress를 제어할 수 있습니다.
        
    - **검사 공정**: **Strict Event-driven**으로 구동해야 합니다. AI Vision 검사나 센서 판정은 불규칙하므로, 백엔드의 `inspection.pcb.completed` 이벤트가 도착했을 때만 State를 갱신합니다.
        
2. **Phase Transition Lock**: `phase`가 `INSPECTING`으로 바뀌는 순간, 생산 관련 로컬 타이머(`setInterval` 등)는 **즉시 `clearInterval` 및 디스포즈** 처리되어야 합니다.
    

## 4. AGV Dispatch 연동 (Event-driven Architecture)

AGV는 공정의 최종 상태 변화에 반응하는 Subscriber 역할을 해야 합니다.

```
[ Line 검사 공정 ] 
       │
       ├─ inspection.pcb.completed (반복) ──> UI 검사 Progress Bar 갱신
       │
       └─ inspection.batch.completed (발생)
              │
              ▼
   [ AGV Dispatcher Service ]
              │
              ├─ 1. 검사 완료 구역(Line Out)으로 AGV 출동 명령
              ├─ 2. Line Phase를 'TRANSFERRING'으로 업데이트
              └─ 3. 적재 완료 시 'IDLE' 전환 및 다음 Batch Waiting Queue 팝업
```

- **안전장치(Fallback)**: 만약 `inspection.batch.completed` 이벤트를 유실하더라도, `inspectionCompleted == batchSize` 조건을 충족하면 AGV Dispatcher가 자체 판단으로 이송 작업을 트리거할 수 있도록 백엔드에서 보충 로직을 갖추는 것이 안전합니다.
