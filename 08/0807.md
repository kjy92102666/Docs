
# 🏭 공정상태(Process Status) 전체 프로세스 및 로직 현황

> 현재 프로젝트에 구축된 공정상태(Process Status) 전체 프로세스 및 로직을 요청하신 3가지 관점(시나리오, 개발자 로직, 시스템 구조)으로 나누어 설명해 드립니다.

## 🎬 1. 시나리오 형식 (운영/작업자 관점의 흐름)

실제 공장 라인과 작업자가 경험하는 전체 시나리오는 다음과 같이 흐릅니다.

### 📌 [단계 1] 생산 계획 등록 & 배치 생성

- 작업자가 생산 계획을 등록하고 배치를 생성합니다.
    
- 해당 라인이 비어있다면 AGV가 배치(최대 500 PCB)를 싣고 라인으로 즉시 투입됩니다.
    
- 라인에 이미 다른 배치가 작업 중이라면, AGV는 배치를 대기 영역(WAITING ZONE)으로 운송하여 대기시킵니다. _(라인당 대기는 최대 1개)_
    

### 📌 [단계 2] 라인 투입 & YOLO 불량 검사

- AGV가 라인 입구에 도착하면 배치가 라인에 정착합니다.
    
- 라인 점유 확인 후 작업자/시스템이 YOLO 검사를 시작합니다. PCB가 한 장씩 자동 인퍼런스(검사)됩니다.
    

### 📌 [단계 3] 검사 완료 & 후공정 버퍼(BUFFER) 이송

- 라인의 모든 PCB 검사가 완료되면, 시스템이 자동으로 후공정 버퍼 슬롯(1~16번) 중 빈 자리를 예약합니다.
    
- AGV가 라인에서 검사 완료된 배치를 꺼내 버퍼 슬롯으로 이송합니다.
    

### 📌 [단계 4] 라인 해제 & 대기 배치 자동 승격 (연쇄 반응)

- AGV가 배치를 버퍼에 하역하는 순간 기존 라인은 즉시 빈 상태로 해제됩니다.
    
- 동시에 대기 영역(WAITING ZONE)에서 대기 중이던 다음 배치가 자동으로 라인 투입 상태로 승격(Promote)되어 AGV가 라인으로 이동을 시작합니다.
    

### 📌 [단계 5] 작업자 판정 & 파이널 도크(FINAL DOCK) 이송 및 완료

- 배치가 버퍼에 있는 동안, 작업자는 리뷰 화면에서 불량 PCB 이미지를 확인하고 최종 판정을 내립니다.
    
- 모든 검토가 끝나면 최종 품질 판정(NORMAL / DEFECT)이 잠금(Lock)됩니다.
    
- AGV가 배치를 버퍼에서 꺼내 최종 적재공간(FINAL DOCK)으로 이송합니다.
    
- 최종 하역이 끝나면 공정이 비로소 최종 완료(COMPLETED)됩니다.
    

## 💻 2. 개발자 관점에서 보는 로직 (상태 모델 & DB 트랜잭션)

개발자 관점의 핵심은 "작업 상태(status)"와 "물류 위치(logistics_location)"의 완전한 분리 및 DB 트랜잭션 기반 동시성 제어입니다.

### A. 핵심 상태 변수 (Dual State Model)

Plaintext

```
■ production_batch.status (작업 진행 상태)
  CREATED (대기 중)
    └─> LINE_ASSIGNED (라인 수락)
          └─> INSPECTING (검사 중)
                └─> INSPECTED (검사 완료)
                      └─> COMPLETED (최종 완료)

■ production_batch.logistics_location (물류 물리 위치)
  WAITING_AREA
    └─> TO_LINE
          └─> LINE
                └─> TO_POST_INSPECTION_BUFFER
                      └─> POST_INSPECTION_BUFFER
                            └─> TO_FINAL_DOCK
                                  └─> FINAL_DOCK
```

### B. 버퍼 슬롯 및 락(Lock) 제어 (`post_inspection_buffer_slot`)

- **16개의 슬롯 상태를 DB에서 직접 관리:** `EMPTY` ➔ `RESERVED` ➔ `OCCUPIED`
    
- 이송 시작 시 `reserve_empty_buffer_slot()`으로 슬롯 1개를 `RESERVED` 상태로 원자적(Atomic) 예약.
    

### C. 이송 완료 및 자동 승격 트랜잭션 (`LifecycleService.complete_post_inspection_transfer`)

이 백엔드 메서드가 공정 상태 로직의 가장 핵심적인 트랜잭션입니다:

Python

```
# 1. 버퍼 슬롯 OCCUPIED 전환 및 배치 물류 위치 POST_INSPECTION_BUFFER 변경
# 2. 라인 락(SELECT FOR UPDATE) 획득 후 라인 점유 해제
# 3. 대기 배치(CREATED + WAITING_AREA) 존재 여부 조회
# 4. 대기 배치가 존재하면 한 트랜잭션 안에서:
#    - 대기 배치 상태 -> LINE_ASSIGNED, 위치 -> TO_LINE 으로 승격 (Promote)
#    - 신규 transfer_id 발급
# 5. 최종 판정(NORMAL/DEFECT) 자동 계산 시도 (try_lock_final_verdict)
# 6. process.line.released 및 process.batch.promoted 이벤트 반환
```

### D. API 멱등성 (Idempotency) 및 재시도 방어

- 모든 이송 시작/완료 API (`/line-transfer/complete`, `/post-inspection-transfer/complete` 등)는 고유 `current_transfer_id`를 검증합니다.
    
- 네트워크 재시도나 중복 요청이 들어오더라도 DB 상태를 파괴하지 않고 기존 응답을 멱등하게 반환합니다.
    

## ⚙️ 3. 시스템적 관점 (컴포넌트 연동 & 데이터 흐름)

시스템 전체는 React UI + REST API + WebSocket Broadcast + Async Pipeline이 실시간 펍섭(Pub/Sub) 구조로 맞물려 움직입니다.

코드 스니펫

```
sequenceDiagram
    autonumber
    actor Operator as 작업자 / UI
    participant React as React Frontend (ProcessStatus)
    participant WS as WebSocket Server (/ws/process-status)
    participant REST as FastAPI Router & Service
    participant YOLO as Batch Inspection Runner
    participant DB as MySQL DB

    Note over React, DB: 1. 배치 생성 및 라인 투입
    Operator->>REST: POST /api/plans/{id}/batches (배치 생성)
    REST->>DB: LINE & WAITING 조건 검증 (FOR UPDATE)
    REST->>DB: 배치 생성 (LINE_ASSIGNED + TO_LINE)
    REST->>WS: process.batch.created 이벤트 브로드캐스트
    WS-->>React: loadSnapshot() 트리거 -> 화면 AGV 애니메이션 시작

    Note over React, DB: 2. YOLO 불량 검사 진행
    React->>REST: POST /api/batches/{id}/line-transfer/complete
    Operator->>REST: POST /api/inspections/batches/{id}/start (검사 시작)
    REST->>YOLO: BatchInspectionRunner.run() (비동기 수행)
    loop PCB 장별 인퍼런스
        YOLO->>DB: inspection_result 저장
        YOLO->>WS: inspection.pcb.completed 브로드캐스트
    end
    YOLO->>DB: batch status = INSPECTED 변경
    YOLO->>REST: lifecycle_hook(batch_id) 호출

    Note over React, DB: 3. 버퍼 이송 & 대기 배치 승격
    REST->>DB: 버퍼 슬롯 RESERVED 예약 & 이송 시작
    React->>REST: POST /api/batches/{id}/post-inspection-transfer/complete
    REST->>DB: 트랜잭션: [버퍼 OCCUPIED + 라인 해제 + 대기배치 승격(LINE_ASSIGNED)]
    REST->>WS: process.line.released & process.batch.promoted 브로드캐스트
    WS-->>React: 1번 배치 버퍼 도착 + 2번 배치 대기열에서 라인 이동 자동 시작

    Note over React, DB: 4. 판정 잠금 및 파이널 도크 완료
    Operator->>REST: defect_review 확정 (판정 검토)
    REST->>DB: final_quality_verdict 잠금 (verdict_locked_at)
    React->>REST: POST /api/batches/{id}/final-dock-transfer/complete
    REST->>DB: status = COMPLETED, logistics_location = FINAL_DOCK
    REST->>WS: process.batch.completed 브로드캐스트
```

## 오늘 공정상태(AGV 미동작) 문제 원인 정리

### 증상

계획 등록 → 배치 생성까지는 되는데, 공정상태 화면에서 AGV가 전혀 움직이지 않고, 검사 시작을 눌러도 `409 BATCH_NOT_ON_LINE`이 남.

### 근본 원인 ① — `ConnectionManager.disconnect()`의 `ValueError`

[backend/app/core/websocket.py](vscode-webview://0tsq27c9mcldp57vk9voq42epj46c5mmn6d5u1p3jflgg04kc9e3/backend/app/core/websocket.py)의 `/ws` 채널에서, 같은 소켓을 두 경로(정상 종료 핸들러 vs `broadcast()`의 실패 처리)가 동시에 제거하려 하면 `list.remove()`가 이미 없는 값에 `ValueError`를 던졌습니다. 이 예외가 `broadcast()`의 반복문을 조기 종료시켜서, 목록에서 그 뒤에 있는 다른 연결들은 이벤트를 아예 못 받았습니다. → **수정**: `disconnect()`를 멱등하게(`if websocket in self.active`) 만듦.

### 근본 원인 ② — `datetime` 직렬화 실패로 인한 전체 연결 유실 (결정적 원인)

`batch_created`/`plan_created` 브로드캐스트 payload가 `SELECT *`로 가져온 DB row(=`datetime` 값 포함)를 그대로 담고 있었는데, `send_json`은 내부적으로 `json.dumps`(커스텀 인코더 없음)를 써서 `TypeError`가 발생했습니다. ①을 고친 뒤로 이 예외는 조용히 잡히긴 했지만, **같은 payload가 모든 연결에 동일하게 실패**하기 때문에, 그 순간 연결돼 있던 클라이언트 전원이 서버의 `active` 목록에서 한꺼번에 사라졌습니다. 브라우저 쪽 실제 WebSocket 연결은 안 끊긴 채로 — 그래서 "연결됨" 표시는 정상인데 이후 어떤 이벤트도 못 받는 상태가 됐습니다. Node.js 프로브로 `active:3 → (브로드캐스트) → active:0`을 직접 재현해서 확정했습니다. → **수정**: `broadcast()`에서 `fastapi.encoders.jsonable_encoder`로 payload를 미리 직렬화 가능한 형태로 바꾼 뒤 전송.

### 함께 고친 부수 문제들 (오늘 라이브 테스트 중 발견)

- `frontend/src/api/websocket.js`의 `connectEvents`에 재연결 로직이 아예 없었음 → 재연결 로직 추가.
- `AgvLineControl.jsx`가 새 스냅샷을 받을 때마다 시뮬레이션을 처음부터 다시 만들어서, 진행 중이던 AGV 애니메이션이 리셋됨 → 진행 중인 이송을 `transfer_id`로 매칭해 이어받는 로직 추가.
- `agvSimulation.js`의 `updateProduction()`이 실제 배치에도 예전 데모용 180초 타이머로 생산량을 가짜로 올리고 있었음 → `serverBatchId`가 있는 라인은 제외.
- `emptyLine()`이 `pcbType`을 안 지워서 빈 라인에 데모 PCB 라벨이 남아있었음 → 초기화 시 `pcbType: null` 추가.

모두 TDD로 재현 테스트 먼저 작성 → 실패 확인 → 수정 → 통과 확인했고, 백엔드 전체 테스트(188개, 무관한 스킵 1건) 통과 상태입니다. 테스트 진행하시고 결과 알려주세요.

Node.js 프로브로 `active:3→0` 직접 재현해서 확정.
3. `frontend/src/api/websocket.js`에 재연결 로직이 없었음 → 추가.
4. `AgvLineControl.jsx`가 새 스냅샷마다 시뮬레이션을 처음부터 재생성해서 진행 중이던 AGV 애니메이션이 리셋됨 → `transfer_id`로 진행 중인 이송을 이어받도록 수정.
5. `agvSimulation.js`가 실제 배치에도 데모용 180초 타이머로 가짜 생산량을 올리고 있었음 → `serverBatchId` 있는 라인은 제외.
6. `emptyLine()`이 `pcbType`을 안 지워 빈 라인에 데모 라벨이 남아있었음 → 수정.

**실측 확인**: 오늘 마지막 테스트에서 배치 등록 즉시 AGV가 실제로 라인까지 이동했고, 검사 완료 후 검사 후 적재공간(BUFFER)까지의 이동도 성공했습니다. 핵심 버그는 해결된 것으로 판단합니다.
