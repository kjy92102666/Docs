# 공정상태 시뮬레이션 규칙 문서

## 1. Batch 등록 및 라인 배정 규칙

### 백엔드 라인 배정 기준

|**라인 상태**|**조건**|**결과**|
|---|---|---|
|**빈 라인**|현재 검사 Batch 없음|`LINE_ASSIGNED`|
|**같은 모듈 검사 중**|대기 Batch 없음|`CREATED` (대기 Batch 1건)|
|**같은 모듈 검사 중**|이미 대기 Batch 존재|등록 거부|
|**다른 모듈 검사 중**|대기 여부와 관계없이|등록 거부|

> **주의:** 검사 시작은 `LINE_ASSIGNED`, `INSPECTING` 상태만 허용합니다. `CREATED`는 대기 Batch이므로 검사할 수 없습니다.

## 2. Line 작동 순서

정상적인 한 Batch의 Line 상태 흐름은 다음과 같습니다.

Plaintext

```
배치 전달 대기 
  → 배치 전달 중 
  → 배치 인계 중 
  → 배치 인계 완료 
  → 생산 중 
  → 검사 완료 
  → PCB 픽업 중 
  → 최종 적재 중 
  → 배치 등록 대기
```

- 이후 다음 Batch가 등록되면 다시 '배치 전달 대기'부터 반복됩니다.
    
- Line 생산은 현재 Batch 수량을 기준으로 **180초 동안 진행**되며, 생산량이 Batch 수량에 도달하면 검사 완료 상태가 됩니다.
    

## 3. 빈 라인의 Batch 투입

빈 라인에 `LINE_ASSIGNED` Batch가 등록되었을 때의 처리 흐름입니다.

1. 전용 AGV를 우선 선택 (전용 AGV가 없으면 지원 AGV 선택)
    
2. AGV 출차 대기
    
3. Dispatch Gate 통과
    
4. Line 입고 도킹 지점으로 이동
    
5. 5초간 Batch 인계
    
6. 빈 AGV 복귀
    
7. AGV가 대기 상태로 돌아오면 Line 생산 시작
    

### AGV 상태 전이 흐름

Plaintext

```
대기 중 → 출차 대기 → 이동 중 → 작업 중 → 복귀 대기 → 복귀 중 → 대기 중
```

## 4. 검사 중 Line의 대기 Batch

같은 모듈이 검사 중이고 대기 Batch가 하나 등록되었을 때의 처리 흐름입니다.

- 대기 Batch는 해당 Line의 `waitingQueue`에 등록됩니다.
    
- 해당 Line의 물리적 Waiting Slot 하나를 사용합니다. (대기 가능한 Batch는 **Line당 최대 1건**)
    
- 대기 AGV가 Waiting Zone으로 이동하여 Waiting Slot에서 대기합니다.
    
- 현재 Batch의 생산·검사·출고가 끝나면 다음 Batch를 Line으로 투입합니다.
    
- 투입 후 대기 Batch는 `LINE_ASSIGNED` 성격으로 변경되어 생산을 시작합니다.
    

### 처리 프로세스

Plaintext

```
대기열 등록 
  → Waiting Zone 이동 
  → Waiting Slot 대기 
  → 기존 Batch 완료 
  → Waiting AGV Line 투입 
  → Batch 인계 
  → 생산 시작
```

## 5. 검사 완료 후 이동

생산량이 Batch 수량에 도달하면 검사품 픽업 AGV가 미리 대기합니다.

- **사전 이동:** 생산량이 약 **85% 이상**이 되면 AGV를 검사품 픽업 위치로 사전 이동시킵니다.
    
- **검사 완료 후 절차:**
    
    1. 검사품 픽업 및 AGV에 Batch 전체 수량 적재
        
    2. 최종 적재 장소로 이동 후 적재 완료
        
    3. 빈 AGV로 복귀
        
    4. Line을 **'배치 등록 대기'** 상태로 변경 (다음 Batch 등록 가능)
        

### 처리 프로세스

Plaintext

```
생산 중 
  → 검사품 픽업 위치 사전 이동 
  → 검사 완료 대기 
  → 검사품 픽업 
  → 최종 적재 
  → 공차 복귀 
  → 다음 Batch 등록 대기
```

## 6. 충전 규칙

- **충전 대상:** 배터리가 **30% 이하**인 대기 AGV
    
- **충전 슬롯:** 최대 **6개** 운영
    
- **절차:** 충전 슬롯 예약 → 충전소 이동 → 충전율 **80% 달성 시 종료** → 슬롯 해제 후 AGV 홈으로 복귀 → 대기 상태 전환
    
- **제어 규칙:** 충전 이동, 출차, 복귀는 Gate를 사용해 한 번에 하나씩 직렬 처리합니다.
    

## 7. AGV 공통 이동 규칙

- **AGV 보유 현황 (총 12대):**
    
    - `AGV-01` ~ `AGV-08`: 각 Line 전용
        
    - `AGV-09` ~ `AGV-12`: 여러 Line 지원 (지원 AGV)
        
- **배정 및 순서 규칙:**
    
    - 전용 AGV를 우선 배정합니다.
        
    - 여러 AGV가 출차 대기 중이면 `dispatchOrder` FIFO 순서를 적용합니다.
        
    - Waiting Queue도 Line별 FIFO 순서를 따릅니다.
        
- **물리적 제약 사항:**
    
    - AGV 최대 적재량: **500 PCB** (Tray당 16 PCB)
        
    - AGV 간 최소 외곽 간격: **4.5m**
        
    - 출차, 복귀, 충전 진입은 Gate로 직렬 제어합니다.
        

## 8. 구현 및 연동 주의점

AGV 시뮬레이션 자체는 다음 비즈니스 규칙을 직접 판단하지 않습니다.

- 같은 모듈인지 여부
    
- `LINE_ASSIGNED`인지 `CREATED`인지 여부
    
- 다른 모듈 검사 중 등록 거부 여부
    

해당 판단은 **백엔드 Batch 등록 로직**이 담당하며, 프론트 시뮬레이션은 `batch_created` 이벤트를 수신하여 대기열이나 전달 흐름에 반영합니다.

따라서 공정상태 작업 시 향후 이벤트에 아래 상태 정보를 포함하는 것을 권장합니다.

JSON

```
{
  "batch_status": "LINE_ASSIGNED | CREATED",
  "model_id": "string",
  "line_id": "string",
  "batch_quantity": "number"
}
```

### 핵심 제어 흐름 요약

Plaintext

```
백엔드가 Batch 등록 가능 여부 결정
  ↓
LINE_ASSIGNED  → 즉시 Line 투입
CREATED        → Waiting Zone 대기
  ↓
AGV 시뮬레이션이 전달·생산·검사품 출고를 상태 전이로 표현
```




























# 검사 이벤트 공정상태 전달 및 시뮬레이션 연동 방안

## 1. 검사 이벤트 전달 구조 개선

검사 화면과 공정상태 화면이 동일한 이벤트를 처리할 수 있도록 **공용 WebSocket 채널(`/ws`)로 이벤트 전달 구조를 통합**합니다.

### 수신 대상 검사 이벤트 목록

- `inspection.batch.started`
    
- `inspection.pcb.started`
    
- `inspection.pcb.completed`
    
- `inspection.pcb.failed`
    
- `inspection.batch.completed`
    
- `inspection.batch.failed`
    

> **아키텍처 제안:** 별도의 WebSocket을 공정상태에 추가 연결하는 방식은 연결 관리 및 재연결 로직이 중복되므로, 기존 공용 이벤트 채널을 확장하는 편이 안정적입니다.

## 2. 실제 검사 진행률의 Line 진행률 반영

기존에는 `currentQuantity / batchSize` 방식으로 계산하여 생산이 끝나면 이미 100%가 되어 실제 검사 진행률(예: 10%)을 정확히 표현하지 못하는 문제가 있었습니다.

### Line 데이터 구조 분리

Line 상태 객체에 다음 값들을 분리하여 안전하게 관리합니다.

- `productionProgress` (생산 진행률)
    
- `inspectionTotal` (검사 대상 총 수량)
    
- `inspectionCompleted` (검사 완료 수량)
    
- `inspectionProgress` (검사 진행률)
    

### 화면 표시 규칙

|**Line 상태**|**화면 표시 진행률**|
|---|---|
|**생산 중**|생산 진행률 (`productionProgress`)|
|**검사 중**|검사 진행률 (`inspectionProgress`)|
|**검사 완료**|100%|
|**최종 적재 중**|100%|
|**배치 등록 대기**|0% (또는 다음 Batch 기준)|

- `inspection.batch.started` 이벤트 수신 시 검사 진행률을 **0으로 초기화**합니다.
    
- `inspection.pcb.completed` 이벤트 수신마다 **완료 수량을 업데이트**하여 진행률을 반영합니다.
    
- _주의: 기존 `currentQuantity`를 검사 진행률로 재사용하면 생산량과 검사량의 의미가 섞이므로 엄격히 분리합니다._
    

## 3. 검사 시작·완료와 AGV 이동 연동

현재 구축된 AGV 주요 목적지(Waiting Zone, Line 입고 도킹, 검사품 픽업 위치, 최종 적재 공간, 공차 복귀, 충전 공간) 및 경로를 그대로 활용합니다.

### 메인 Batch 처리 프로세스

Plaintext

```
Batch 등록
  ↓
LINE_ASSIGNED
  ↓
AGV가 Line으로 Batch 운반
  ↓
생산 중
  ↓
검사 시작 이벤트 (inspection.batch.started)
  ↓
Line 검사 중 전환 + 검사 진행률 반영
  ↓
검사 완료 이벤트 (inspection.batch.completed)
  ↓
검사품 픽업 AGV 이동
  ↓
최종 적재 공간 이동
  ↓
공차 복귀
  ↓
다음 Batch 등록 대기
```

### 대기(CREATED) Batch 처리 프로세스

Plaintext

```
CREATED
  ↓
Waiting Queue 등록
  ↓
Waiting Zone 이동
  ↓
Waiting Slot 대기
  ↓
현재 Batch 출고 완료
  ↓
Line 투입
  ↓
생산 시작
```

> **기존 규칙 유지:** Waiting Queue 1건 제한, 전용 AGV 우선 배정, 지원 AGV Fallback, FIFO, 충전 우선순위 등은 기존 로직을 그대로 재사용합니다.

## 4. 현재 구조의 위험 요소 및 예방책

### ① WebSocket 이벤트 채널 분리 문제

- **위험:** 검사화면과 공정상태가 서로 다른 WebSocket을 사용하여 공정상태가 검사 이벤트를 수신하지 못함.
    
- **해결:** 이벤트 전달 구조를 공용 채널로 통합하는 작업을 최우선 진행.
    

### ② 로컬 시뮬레이션 타이머와 실제 검사 이벤트 충돌

- **위험:** 프론트엔드 타이머 기반 생산 완료 시점과 백엔드 실제 검사 완료 시점이 불일치함.
    
- **원칙 수립:**
    
    - **생산량:** 기존 시뮬레이션 또는 백엔드 Batch 상태 기준
        
    - **검사 상태·진행률:** 백엔드 검사 이벤트 기준
        
    - **검사 완료 후 AGV 출고:** 백엔드 `inspection.batch.completed` 이벤트 기준
        

### ③ 이벤트 재연결 및 중복 수신 문제

- **위험:** 네트워크 재연결, 이벤트 중복 수신, `pcb.completed` 순서 역전, 공정상태 화면 지연 진입으로 인한 과거 이벤트 누락.
    
- **해결:**
    
    - `batch_id`, `line_id`, `event_version`, `completed` 수량을 검증하여 중복 및 유효하지 않은 이벤트를 무시.
        
    - WebSocket 재연결 시 현재 Batch 상태를 백엔드에서 다시 조회(REST API)하는 **보정(Reconciliation) 로직** 도입.
        

### ④ `line_id` 식별자 형식 차이

- **위험:** 백엔드는 숫자형(`1`), 프론트엔드 시뮬레이션은 문자열(`LINE-01`) 사용.
    
- **해결:** 이벤트 수신 시 단일 포맷으로 데이터 정규화(Normalization) 필수 적용.
    

### ⑤ AGV 충전 또는 다른 작업 중 검사 완료 발생

- **위험:** 검사 완료 이벤트 도착 시 대상 AGV가 충전 중이거나 다른 라인을 지원 중인 경우.
    
- **해결:** AGV를 즉시 강제 이동시키지 않고, 기존 Dispatch Queue에 '검사품 픽업' 작업을 큐잉(Queueing)하여 순차 처리.
    

## 5. 단계별 작업 순서 제안

1. **이벤트 통합:** 검사 이벤트를 공용 WebSocket 채널로 전달 구조 변경
    
2. **이벤트 리듀서(Reducer) 작성:** 공정상태에서 검사 이벤트를 수신할 수 있는 Reducer 구현
    
3. **진행률 데이터 분리:** Line 객체 내 생산 진행률과 검사 진행률 필드 분리
    
4. **상태 전이 구현:** 검사 시작 / 진행 / 완료 / 실패 이벤트별 Line 상태 전이 로직 작성
    
5. **AGV 동선 연결:** 검사 완료 후 `검사품 픽업 → 최종 적재 → 공차 복귀` 순서 제어 연동
    
6. **대기열 연동:** Waiting Zone 내 대기 Batch가 Line으로 승격되는 승격 흐름 연동
    
7. **예외 처리 테스트:** 재연결, 이벤트 중복, AGV 작업 중 상황에 대한 시나리오 테스트 작성
    
8. **통합 테스트:** 실제 이벤트 순서 기반 전체 시뮬레이션 통합 테스트 실행
    

### 💡 결론 및 요약

기존에 구축된 AGV 경로 및 상태 모델을 그대로 재사용할 수 있어 전체 구조 변경 없이 개발 가능합니다. 단, 단순히 `inspection.batch.completed` 이벤트 하나만 수신받아 처리하면 시뮬레이션 상태가 꼬일 수 있으므로, **WebSocket 채널 통합**과 **Line 진행률(생산 vs 검사) 분리**를 최우선으로 설계한 뒤 단계적으로 적용하는 것을 권장합니다.
